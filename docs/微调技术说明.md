# 数据结构智练：微调实验设计与操作说明

**状态：已提供数据和脚本，尚未运行真实 GPU 训练。本文描述可执行方案，不包含虚构训练指标。正式报告需补充实际硬件、日志、耗时和评测结果。**

## 1. 任务与方法

选用 Qwen/Qwen3-1.7B 作为基座，目标是学习数据结构刷题场景中的提示、作答解释和知识点追问。题库负责客观题判分，模型根据题干和参考资料进行辅导。该方案的微调目标是回答方式与指令遵循，不是通过少量样本训练出新的通用解题能力。

LoRA 冻结原始权重 W，只训练低秩增量矩阵，形式为 W' = W + (α/r)BA。参数 r 控制低秩容量，α/r 控制增量缩放。当前脚本对线性层添加 LoRA，r=8、α=16、dropout=0.05。此设置是初始实验配置，并非已经验证的最优值。

默认采用普通 LoRA。在单卡 24GB GPU 上对 1.7B 模型开展短序列小批次实验，以首次实测显存为准。增加 `--quantize` 可启用 QLoRA：以 4-bit NF4 加载基座、启用双重量化，仅更新 LoRA 参数。QLoRA 能降低基座内存需求，但可能改变数值表现；比较时应保证基座和微调模型使用相同量化配置。

## 2. 数据与划分

原始题库是项目自编的 60 道单选题，六个章节各 10 道。每题包含题干、四个选项、标准答案、提示、解析、知识点、易错点、题族标识。内容经过编写时检查及部分计算题程序校验，仍应由课程学习者或教师逐题复核。

每道题通过固定模板构造四种样本：只给提示、正确作答后的解析、错误作答后的解析、知识点追问。因此 240 条样本不等于 240 道独立题目。模板生成的语言多样性有限，可能让模型过拟合固定表达。

`prepare_data.py` 使用随机种子 42，在每个章节内按题族划分：36 道训练题形成 144 条样本；12 道验证题形成 48 条样本；12 道测试题形成 48 条样本。一个题族的所有变式必须留在同一集合。训练前再次检查题族不相交。验证集用于选择检查点，测试集仅用于最终对比，不能根据测试表现反复调整参数。

重要限制：解析类输入包含标准答案和参考解析。因此评估考察的是“参考资料给定时的辅导质量”，不能把这种结果描述为闭卷答题正确率。若要测试独立解题能力，需要另建没有答案提示的题目集和实验。

数据保存在 `data/training/*.jsonl`，每行包含 question_id、task 和 messages。`manifest.json` 保存划分、题目 ID 和文件 SHA-256，便于确认报告所用数据。

## 3. 云 GPU 环境

优先使用 Linux、Python 3.11、与驱动兼容的 CUDA PyTorch 镜像。先上传源码包并解压，然后在项目根目录执行：

```bash
nvidia-smi
python -c "import torch; print(torch.__version__); print(torch.cuda.is_available())"
python -m pip install -r training/requirements.txt
python training/prepare_data.py
```

不要在本机 Web 虚拟环境中安装整套 GPU 依赖。Web 环境和训练环境分开，可减少依赖冲突。训练脚本未检测到 CUDA 时会退出。

模型默认从 Hugging Face 的官方 Qwen 仓库下载。若云平台网络无法访问，可从官方 Qwen ModelScope 仓库下载同一模型到本地目录，再通过 `--model /实际模型目录` 指定。记录实际模型来源和版本，不要混用不同模型的分词器与权重。

## 4. 先试跑，再正式训练

先执行 5 个优化步的试跑：

```bash
python training/train_lora.py --max-steps 5 --output-dir outputs/smoke
```

确认数据加载、显存、保存均正常后，执行正式实验：

```bash
python training/train_lora.py --output-dir outputs/lora
```

显存不足时可先使用 QLoRA：

```bash
python training/train_lora.py --quantize --output-dir outputs/lora-4bit
```

默认 batch size=1、梯度累积=8、训练 3 个 epoch、学习率 2e-4、最大序列长度 1536、cosine 学习率调度、warmup 比例 0.1、gradient checkpointing 开启。BF16 可用时优先 BF16，否则 FP16。

数据编码只让助手目标回答参与损失计算：system 和 user 对应标签置为 −100，padding 标签也置为 −100。脚本使用 Qwen 对话模板并关闭思考模式；超过最大长度会明确报错，不静默截断训练目标。可根据实测长度调整 max-length，但要在报告中记录最终参数。

输出目录非空时脚本拒绝覆盖。试跑和正式训练分别保存，防止误把试跑权重当作正式结果。

## 5. 应保留的真实证据

训练完成后保存：适配器权重及配置、分词器、`run_metadata.json`、`trainer_state.json`、`loss_history.json`、`loss.png`。metadata 包含实际 GPU、包版本、数据摘要、时间、显存峰值、参数数量和损失指标。

训练损失下降只能说明对训练目标的拟合改善，不能单独证明泛化性能提高。需要保存失败和不改善的样例，并在讨论中如实说明。

## 6. 微调前后公平对比

```bash
python training/evaluate.py --adapter outputs/lora
```

若训练使用 4-bit，并希望在量化条件下评测：

```bash
python training/evaluate.py --adapter outputs/lora-4bit --quantize
```

脚本加载同一个基座，分别禁用和启用同一个适配器，对相同测试提示采用相同确定性解码参数。先预热，再交替执行基础与微调模型，保存真实回答和响应时间。单次计时仅作参考，严格速度比较还需要多次重复、固定负载和统计分布。

输出 `results.jsonl`、`metadata.json` 和 `human_review.csv`。人工评分列初始为空：

- 正确性：0/1，解释是否符合题目和参考解析。
- 清晰度：1～5，步骤是否足以帮助理解，是否冗长或含混。
- 提示泄露：只针对 hint 样本，0 表示未泄露，1 表示泄露最终答案或选项；其他任务留空。
- 备注：记录事实错误、格式违约、答非所问等现象。

建议隐藏模型来源后交叉评分；报告注明评审人数、标准、样本数和局限。测试集只有 12 道独立题目，四种变式不是四个独立问题，不宜推导广泛的性能结论。不要把商用大模型 API 与本地小模型的差异当成 LoRA 带来的提升。

把 `outputs/evaluation/` 下载回本机同路径，即可在网页“模型实验室”查看真实结果。实际推理服务启动见《使用与部署说明》。
